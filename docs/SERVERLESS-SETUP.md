# APD serverless integration — deployment gate

This extends the existing portal and Firebase project. It requires no persistent computer, Gateway connection, public local port, paid hosting, or Firebase Cloud Functions. Current production has NOT been migrated by this change.

## Deployment order
1. Confirm the Firebase project is rattler-nation-apd and its plan remains Spark. Back up existing Firestore rules in the console and export important records through authorized access. Preserve all accounts. The checkpoint-before-discord-bot Git tag preserves the original source; it does not back up database records.
2. Run the emulator security tests, review firestore.rules, and deploy rules/indexes only after checking the current collection schemas. Explicitly grant cidEditor to existing authorized CID staff and officer/reviewer permissions as appropriate. The old calendarEditor permission no longer grants CID access. Preserve current owner admin flags; never grant membership users admin.
3. Sign into Cloudflare using Wrangler OAuth and confirm Workers Free. Do not enable billing. The Worker is now deployed; reauthenticate only if the CLI authorization expires. Install worker dependencies with npm ci in worker/.
4. Create/configure a Discord application in the official Developer Portal. Confirm the server name AND guild ID with the owner before installation. Install with bot and applications.commands scopes. Grant only View Channels, Send Messages, Embed Links, Read Message History, Manage Channels, and Manage Roles as needed by the approved wizard. Do not grant Administrator. To notify the non-mentionable APD role, Discord also requires the bot to have Mention Everyone/Roles permission in the announcement destination. Grant this to the bot only for approved publish channels; the application still explicitly prohibits everyone/here and restricts allowed role IDs. Without that permission a displayed role mention may not notify members. Enable Server Members intent only if scheduled reconciliation is enabled. Position the bot role above the roles it manages.
5. Use worker/scripts/Set-Secrets.ps1 for hidden-input uploads after login, or store DISCORD_BOT_TOKEN, DISCORD_PUBLIC_KEY, DISCORD_APPLICATION_ID, DISCORD_GUILD_ID, FIREBASE_CLIENT_EMAIL, FIREBASE_PRIVATE_KEY, and FIREBASE_WEB_API_KEY through wrangler secret put. Use the official interfaces and local hidden input; never paste credentials into chat or commit keys. The Firebase web API key is public configuration; the service-account private key is a secret. Use a dedicated service account with only required Firestore permissions. No billing upgrade is required by this design.
6. Deploy from worker/ with Wrangler. Test /health and set the exact deployed HTTPS URL in discord-runtime-config.js. In the Developer Portal set the Interactions Endpoint URL to that URL plus /interactions; Discord must verify the signed handshake.
7. Sign into the existing website as owner. Register commands, review docs/DISCORD-SERVER-LAYOUT.md, and approve the setup wizard. It reuses compatible existing roles/channels, creates missing entries in bounded steps, and saves IDs. Confirm restricted channel access using an ordinary officer before sending confidential notifications.
8. Configure channel destinations and authorized role mentions. Send approved non-sensitive test messages. Only after successful integration tests should the frontend changes be published to the existing GitHub Pages repository/URL.
9. Request explicit approval to revoke the six exposed legacy webhooks. Revoke each in Discord and verify the old endpoint is invalid. Removal from current source alone does not revoke a token or remove Git history exposure. The ignored worker/.secrets backup is temporary sensitive material; remove it after approved rotation and verification.

## Acceptance tests — live tests still required
Verify member-role assignment, denied unauthorized rank changes, announcement creation/edit/deletion and non-repeated pings, replay suppression, attendance, account linking, private warrants/OIS/CID, reviewer permissions, Worker restart/retry recovery, unavailable backend behavior, and the actual Spark/Free plan settings. Local mocks and emulator tests are not live Discord tests.

## Free-tier and reliability limits
Workers Free has documented request/CPU/subrequest limits; Firestore Spark has daily read/write/delete and storage quotas. These are finite, and deployment CPU behavior must be measured with the actual account. The implementation bounds jobs (default 300 per day), steps server setup and role sync, and scans small batches. Other requests, snapshots, repeated malicious requests, and Discord interactions also consume quota. No billing is enabled by source code and no paid fallback is configured. Quota exhaustion can delay or stop service.

Cron jobs are periodic and may be delayed. APD membership reconciliation is disabled by default; when enabled it scans up to ten members per ten-minute interval, requires Members intent, and is not immediate join detection. Large servers need multiple intervals. Verified /link onboarding is the alternative. Neither approach automatically grants ranks or privileged website access.

Messages with uncertain delivery after a crash enter manual_review rather than blindly retrying and possibly pinging twice. Check Discord and the receipt before recovery. Failed deliveries can be retried through the owner console. Announcement source/audit/job writes are atomic. Some legacy calendar/CID flows still save their source separately from the activity log, so inspect delivery status rather than assuming every saved record was sent.

## External documents and forms
Existing Google roster, SOP, warrant templates, and Google Forms remain in place. They are not automatically imported. integrations/google-forms-notifications.gs is an optional form-bound trigger requiring explicit installation and authorization. Its HMAC-authenticated notification contains only form type and response ID; no private answers are sent to Discord. It is not currently installed.

## Remaining scope
The current implementation includes the core workflows, but does not yet provide every requested enhancement: all notification templates, comprehensive security-center coverage, full visual/accessibility QA remain pending. Do not represent them as deployed functionality.

Activation gate: after confirming Workers Free and successful Discord setup/private-permission tests, set INTEGRATION_ENABLED=true and redeploy. It is deliberately false in the current deployment.
